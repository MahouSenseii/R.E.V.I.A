# R.E.V.I.A audit, 18 October 2026

A review of the whole repository at `96df989` for security, correctness, performance, and the gap to assistants such as ChatGPT, Claude and Codex. Six parallel reviews covered:

- network and inter-process surfaces;
- action and permission enforcement;
- supply chain, self-improvement and privacy;
- correctness and concurrency in the turn path;
- latency;
- assistant capability.

Every finding below was traced in the code. Those marked **fixed** are changed in this commit, each with a regression test unless stated otherwise.

**How it was verified.** This review ran on Linux, so the full Windows/Qt build and the CTest suites could not run. Verification was done this way:

- The policy, authorization and prompt-builder code was compiled and the changed tests run against the real sources with g++. Each new test was also run against the original code, where it fails.
- The relay suite was run with Node: 47 pass, 1 skipped (Windows-only).
- The voice-monitor race was checked with ThreadSanitizer.
- Every changed C++ file was syntax-checked for the Windows target with MinGW-w64 GCC 13 (`-Wall -Wextra`): no errors, no warnings.
- The full suites, including the PowerShell 5.1 parse job, run in CI on push.

## Bottom line

- **Safety plumbing:** strong. Typed `ActionRequest`s, `CapabilityPolicy`, confirmation, audit, cancellation, the process allowlist, guarded writes and the self-modification barrier all held up under review. The one real escape (ACT-1) was a gap between two of these layers, and it is closed here.
- **Where Revia trails ChatGPT and Claude:** the assistant core, not safety.
  - Replies are buffered until fully generated.
  - The model never chooses a tool in chat; phrase lists decide before it runs.
  - Context is 8K tokens.
  - There is no file or image input, no code interpreter, no MCP, and no markdown chat UI.
  - Several serial model calls run before every answer.

  The roadmap in §5 orders these by impact over effort.

## 4. Performance: where the latency goes

A typed question today runs these steps in series:

1. archive write;
2. routing;
3. self-inquiry: an embedding, a memory search, then a non-streamed model call of up to 720 tokens;
4. three health GETs;
5. a second embedding;
6. memory search;
7. `/apply-template` plus `/tokenize`;
8. prefill;
9. **decoding the entire reply**;
10. filters.

Only then does text appear and speech start.

| ID | Impact | Change | Estimated gain |
|---|---|---|---|
| PERF-1 | **High** | Stream text and speech by sentence through the existing `GuardStreamedPrefix` gate, instead of `ConversationAgent` discarding deltas and delivering once (`conversationAgent.cpp:22-24, 101-105`). The README's "starts speaking after the first sentence" is not what happens today. | First text from about 3.3 s to about 0.6 s; first audio from about 4.3 s to about 1.5 s |
| PERF-2 | **High** | Self-inquiry runs on every question (`selfInquiryScope: "questions"`). Use `"hard"` now, then replace it with Qwen3.5's built-in thinking mode, streamed into the existing "Thought process" view. | 2–4 s on question turns |
| PERF-3 | High | The prompt cache is probably not reused: history is trimmed by one exchange every turn once full, and the runtime block moves between messages. First, log `timings.cache_n`. Then trim with hysteresis (drop to about 60%) and keep historical messages byte-stable. | 0.15–1 s late in a session |
| PERF-4 | Medium-High | One llama slot serves everything, and background calls use `stream:false`, so cancelling them is slow. Stream them; use `--parallel 2` with slot 0 for chat. | Up to about 1 s on quick follow-ups |
| PERF-5 | Medium | Memory classification (about 7.5 s) starts at the same moment as the first TTS phrase, on the same GPU. Defer it until speech drains. | 0.3–1 s to first audio |
| PERF-6 | Medium | A 350 ms merge window plus 200 ms polling on voice input. Wake on a condition variable instead, and skip the merge for push-to-talk. | 250–450 ms per voice turn |
| PERF-7 | Medium | The embedding is synchronous, computed twice, has 3 CPU threads (chat on the GPU has 11), and long queries may exceed the 512-token batch. Add an LRU cache, run it with `std::async`, and rebalance threads. | 30–150 ms, plus restored recall on long queries |
| PERF-8 | Medium | 350 ms of fixed silence after every phrase. Use `waveOut` completion callbacks. | About 1.75 s over a 6-phrase reply |
| PERF-9..14 | Low-Medium | The first fragment waits for a whole sentence. Health checks and the tokenize call run on every turn. The chat window rebuilds the full HTML on every entry. Studio panels hit SQLite and fsync every second. Vision runs every 30 s on the chat GPU. Brute-force cosine search re-normalizes every vector. | Each 10 ms to 0.8 s |

Already well optimized:

- **SQLite:** WAL, FTS5 with bm25 ranking, real indexes.
- **Scheduling and prompt setup:** the user's turn preempts background calls; `cache_prompt` and `--cache-ram` are set.
- **Reflex lane:** 18 ms.
- **TTS:** CUDA-graphed (RTF about 0.3), resident models, cached voice-clone prompts.
- **Background work:** debounced, and yields to the user.

## 5. Capability gap to ChatGPT, Claude and Codex

| Dimension | Rating | Key evidence |
|---|---|---|
| Tool and function calling | Weak | The chat request has no `tools`. Phrase lists pick at most one web lookup per turn. Real tool loops exist only in Agent Studio (at most 4 steps) and `/goal`. |
| Structured output | Strong | `response_format.json_schema` with validation. |
| Context management | Weak | 8K tokens everywhere, older turns truncated to 3.5 KB, and "summaries" are keyword-scored excerpts. The project's own benchmark shows the 4B model keeps every fact at 32K. |
| Memory | Partial | Hybrid BM25 + vector + RRF, but no forget or pin, no reranker, and paraphrases pile up. |
| Reasoning | Partial | Thinking only on the Deep route and sharing the 1,024-token cap; `reasoning_content` is ignored; the calculator only does + − × ÷. |
| Code assistant | Weak | No grep, patch or test tools; process execution is off; `/improve` only reviews her own source. |
| Web research | Partial | One DuckDuckGo query per turn, at most 3 pages; citations are a prompt instruction. |
| Multimodal input | Weak | No paste, drop or attach; no PDF. |
| Extensibility | Missing | No MCP and no OpenAI-compatible API. |
| Evaluation | Partial | Strong campaign machinery, but 6 + 6 cases scored by phrase detectors, and the semantic oracle is a stub. |
| Chat UX | Weak | Escaped text with `<br>`; no markdown, code blocks, copy, regenerate, edit, multiple chats or export. Stop works. |

### Roadmap, ordered by user-visible impact over effort

1. **Stream replies** (S–M). This is PERF-1, and it makes Revia feel twice as fast.
2. **32K context and real compaction** (S, then M):
   - Set `llm.contextSize: 32768` with a q8_0 KV cache.
   - Raise the `conversationContext` caps.
   - Summarize evicted turns in the background with the model, queued like `MemoryAgent`.
3. **Native thinking instead of self-inquiry** (S–M). Give thinking its own token budget, stream `reasoning_content` into "Thought process", and let the model decide the effort.
4. **Baseline chat UX** (M). Markdown with `QTextDocument::setMarkdown(…, MarkdownNoHTML)`, code blocks with Copy, regenerate, edit-and-resend, and a chat sidebar backed by the existing FTS5 archive.
5. **A native tool loop in chat** (L):
   - Build a tool registry from the effective permissions.
   - Send `tools` and parse `tool_calls`.
   - Execute through `ActionRuntime` with the existing confirmation and audit, for up to 8 steps.
   - First tools: web_search, fetch_page, search_memory, recall_history, read_file, list_dir, set_reminder, generate_image, calculator.
   - Then retire the phrase routers one at a time.
6. **Files, images and PDFs plus document RAG** (M–L). Images go to Main as `image_url`; the projector is already loaded. Documents are chunked into SQLite using the existing hybrid ranking.
7. **A sandboxed code interpreter** (M–L). Python in the VMware guest or Windows Sandbox, then Codex-style repository tools (grep, ranged read, apply_patch, run tests) for the user's own projects.
8. **An evaluation gate** (M). 150–300 golden cases, an LLM judge scoring against the baseline, trend history, and a nightly self-hosted run that blocks on regressions. Start this early, because items 3 and 9 need it.
9. **Models, and an opt-in cloud fallback** (M):
   - Benchmark Qwen3.5-9B as Main; it has native vision, so the "Unredacted" 8B Expert can go.
   - For a stronger Expert, try a mixture-of-experts model with its experts in system RAM.
   - Optional cloud: an OpenAI-compatible or Anthropic backend, off by default, enabled per turn, payloads redacted and audited.
10. **MCP client and a local API** (L). MCP tools go into the same registry behind `CapabilityPolicy`, and a loopback `/v1/chat/completions` endpoint takes a bearer token.

### Quick wins, each under a day

- Set `conversation.selfInquiryScope` to `"hard"`.
- Set `llm.contextSize: 32768` and verify with `Tools/Quality/contextBenchmark.py`.
- Render markdown in the chat window and add a Copy link per message.
- Add a Forget button that sets `active = 0`; retrieval already filters on it.
- Log `timings.cache_n`, `prompt_n` and `prompt_ms` per turn so PERF-3 is measured rather than inferred.

### Over-engineering that hurts the assistant

Most of these are layers that change the model's text or make decisions for it:

- `ConversationStylePolicy` (1,205 lines) rewrites replies, including canned replacements.
- Phrase routers decide in seven places.
- A 4.9 KB system prompt plus a state packet plus style guidance all compete for 8K tokens.
- `reviaSession.cpp` is 10,000 lines long.

The project's own ROADMAP notes that personality is crowding out substance. The direction that matches ChatGPT and Claude is fewer instructions, more context, and letting the model choose tools. Keep the authority layer exactly as it is: it is what makes that safe.
