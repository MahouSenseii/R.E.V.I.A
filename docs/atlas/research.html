Positive and negative results can point to another workable approach. Two small leads are worth checking: existing prompt-prefix reuse and embedding-cache lifecycle coverage. These are source-supported questions, not measured application improvements.

Observed source, hypotheses and smallest checks

The audit inspected Revia main 1b4118f2 and llama.cpp b10453 source 3cb7ffb1. Revia sends HTTP messages and requests prompt reuse; it does not expose internal matrix inputs. Context, positions and recurrent state can change later hidden vectors even when words repeat. Initial projections could still repeat, but their remaining cost and useful repeat rate are unmeasured.

llama.cpp already reuses common token prefixes and applicable recurrent checkpoints. Exact-input embedding vectors are also cached in Revia, and applying settings clears that cache. These existing mechanisms do not prove actual cache hits or faster real-model execution. Installed identity was unverified in this audit; the later smaller-model artifact check is recorded below. A source pin and model alias alone do not prove the runtime, loaded weights/adapters or application settings.

Lead 1: qualify existing prefix reuse

Observed: the reuse request and backend paths exist, and Revia already retains cached/evaluated token counts and timing fields. Hypothesis: existing reuse may already avoid much of the relevant prompt-processing cost. Smallest later experiment: after separate approval and pinned runtime/model/template/backend identities, compare fixed public shared-prefix and changed-prefix fixtures with reuse requested on/off. Use existing numeric counts, prompt and request times; retain missing metrics as unknown. Keep private prompts and activation telemetry out of the check. The audit did not run or authorize this experiment. The later PREFIX-004 attempt is recorded below.

Lead 2: establish embedding-cache lifecycle coverage

Observed: a model alias appears in the key; normal settings/startup already clears the cache. That is a lifecycle question, not a confirmed bug. Hypothesis: supported model replacements may already invalidate correctly, or may need a stronger generation boundary. Smallest discriminator: inspect the settings/reload call chains first. No new settings-clear test, concurrent-settings race or fix is proposed.

Cache the pure matrix product, then keep updating state. Keying one entry by the selected expert and every input bit preserved all 280 tested steps. Routing, activation and state updates still ran every time.

What we know

The original ZIP was retained, hashed and safely inspected before reviewed CPU execution. Its handcrafted three-input, three-state, three-expert network remains a teaching prototype. The earlier C++ findings are now confirmed against original source.

Static findings and their evidence limits
  • The HTML matrix loop performs nine multiply-add iterations for a new event while its one-hot-input counter displays three. Routing, activation and state-update overhead are outside that counter.
  • The original loader expands nine packed matrix bytes to 27 one-byte indices, with all experts resident. Keeping nine packed bytes in RAM belongs to the new experimental P worker; neither number is total runtime memory.
  • The authored novelty cache skips state updates on repeated inputs even though routing and output depend on state. Its approximate threshold supplies no error bound.
  • Inspection uses E*(N+3)/4 instead of per-expert packing E*((N+3)/4). A 3-input, 1-state, 3-expert fixture measured four reported matrix bytes versus three actual payload bytes; its full file was 107 bytes.
  • The illustration honestly labels 113 full-file bytes versus 108 matrix-only FP32 bytes. These compare different scopes and do not prove total savings.
  • No tokenizer, learned weights, training loop, text inference or GGUF support is demonstrated. The supplied original checks lack full numeric trajectories; FIRST-001 now covers this toy's state, not language quality or VRAM.

Source hashes, full traces, raw timing batches and limits are retained in the reviewed experiment report and evidence summary. The original source was not patched; no research code was merged into Revia.

Path into Revia

Keep useful ideas eligible for later integration. First reproduce the benefit against an unchanged baseline and record tradeoffs. Then review the held-out quality, safety and privacy results and propose a small change. Integration needs explicit authorization and a tested rollback; passing an experiment never merges or replaces a model automatically.

The broader RNL vision is a trainable adaptive/stateful architecture. Cache tests qualify one ingredient; their outcomes do not define or complete that architecture. Other workable approaches need their own evidence and evaluations.

Memory, corrections and future evaluated adapters remain a separate practical learning path. Any future training needs consent-aware data lineage and withdrawal checks. Deleting an example later does not erase its influence from trained weights.
