RNL-003: complete event cost

Reuse can repay its overhead when the same expert and input recur. Across four synthetic matrix sizes, the eight conditions with repeated events met the predeclared timing rule. Median paired uncached/cached time ratios ranged from 1.213 to 3.994. All four zero-repeat controls had zero hits and no benefit.

The result preserves routing and recurrent state updates. It adds retained buffers and does not demonstrate lower RAM. Real Revia repetition, model quality and useful application savings remain unmeasured. No candidate is promoted.

Timing, equality, memory and evidence limits

The protocol was committed before implementation and reviewed before execution. Immutable generated networks used three experts, top-1 and square sizes 16, 64, 256 and 1024. Byte-index decoding and one ordinary matrix kernel were shared by both modes. The original CLI rejects sizes above 256; size 1024 is new synthetic instrumentation.

Repeated events and cache hits differ: state can change the selected expert. At size 1024 with 90% repeated events, 77% were hits. Median complete event times were 773.327 microseconds uncached and 193.596 cached. Ratios above are medians of paired ratios; they are not ratios of separately rounded medians.

Each timing includes routing, key comparisons/copies, decoding and matrix work on misses, activation, state and a common checksum. Generation, reset, validation, final hashing and serialization are excluded. Timings include cache key-comparison counters; their incremental cost was not isolated. No per-multiply counter runs in the timed kernel. U-only calibration, one warmup per mode and five alternating pairs were fixed in advance. Every benefit condition met median U/M at least 1.10, every pair above 1.05 and non-overlapping ranges in the faster direction.

All 12 conditions met the resolution rule: shortest comparison batch 18.98 ms, QPC frequency 10 MHz and smallest positive read gap one tick. Five pairs describe this run, not other hardware or a deployment guarantee. CPU identity was unavailable; outside contention was not controlled.

All 2,400 validation steps matched experts, scores, raw products, outputs and state bits. Independent integer row sums checked every size; the Python FP32 oracle checked all 600 size-16 steps. Timed pairs also matched checksums and final-state hashes. Four independent data checks passed, alongside preserved RNL-002 controls. No timing reruns or kernel tuning followed the results.

The cache added 128, 512, 2,048 and 8,192 bytes of retained buffers as size increased. Both modes used the same VM class, including fixed cache metadata. Separate-process snapshots at size 1024 measured working sets of 7,221,248 bytes uncached and 7,225,344 cached, with private bytes 4,059,136 and 4,067,328. These whole-process readings and partial capacity sums are not a full heap census. Allocator overhead is unknown; empty-worker memory is context, not an exact subtraction. No generated model file was created; scale-study disk-load time was not measured.

One attempt completed 24 native workers and three guarded data checks in 19.516 seconds, retaining about 786 kB before derived publication artifacts. Affinity, 256 MiB working-set/commit caps, deadlines, bounded output and owned-process cleanup were verified. The guard is a resource supervisor, not a security sandbox. No GPU, training, dependencies or application changes ran.

Where this could help Revia

Keep the measured benefit and test the practical fit separately. RNL-003 remains positive evidence for exact reuse on its synthetic repeat workload. A source audit found no current demonstrated target for adding that matrix cache to Revia. Candidate for Revia and Integrated remain None.

Positive and negative results can point to another workable approach. Two small leads are worth checking: existing prompt-prefix reuse and embedding-cache lifecycle coverage. These are source-supported questions, not measured application improvements.

Observed source, hypotheses and smallest checks

The audit inspected Revia main 1b4118f2 and llama.cpp b10453 source 3cb7ffb1. Revia sends HTTP messages and requests prompt reuse; it does not expose internal matrix inputs. Context, positions and recurrent state can change later hidden vectors even when words repeat. Initial projections could still repeat, but their remaining cost and useful repeat rate are unmeasured.

llama.cpp already reuses common token prefixes and applicable recurrent checkpoints. Exact-input embedding vectors are also cached in Revia, and applying settings clears that cache. These existing mechanisms do not prove actual cache hits or faster real-model execution. Installed identity was unverified in this audit; the later smaller-model artifact check is recorded below. A source pin and model alias alone do not prove the runtime, loaded weights/adapters or application settings.

Lead 1: qualify existing prefix reuse

Observed: the reuse request and backend paths exist, and Revia already retains cached/evaluated token counts and timing fields. Hypothesis: existing reuse may already avoid much of the relevant prompt-processing cost. Smallest later experiment: after separate approval and pinned runtime/model/template/backend identities, compare fixed public shared-prefix and changed-prefix fixtures with reuse requested on/off. Use existing numeric counts, prompt and request times; retain missing metrics as unknown. Keep private prompts and activation telemetry out of the check. The audit did not run or authorize this experiment. The later PREFIX-004 attempt is recorded below.

Lead 2: establish embedding-cache lifecycle coverage

Observed: a model alias appears in the key; normal settings/startup already clears the cache. That is a lifecycle question, not a confirmed bug. Hypothesis: supported model replacements may already invalidate correctly, or may need a stronger generation boundary. Smallest discriminator: inspect the settings/reload call chains first. Only if a supported same-alias replacement can preserve the cache would a later approved, quiescent fake-server fixture compare the same public input with orthogonal normalized vectors and HTTP counts. No new settings-clear test, concurrent-settings race or fix is proposed.

A pure matrix-product contract requires exact input bits, matrix/layer identity, effective immutable weights including adapters, and relevant numeric settings. Position/context belongs in the key when directly used by that operation; whole-block reuse also needs causal KV/recurrent state. Existing backend batch differences can affect numeric equality, so the toy's bitwise result cannot be assumed for another kernel.

The documentation step added no telemetry and ran no model calls, tests, GPU/training work or dependency installation. The later read-only embedding lifecycle check did not establish a supported changed-weight cache bug. PREFIX-004 below records its separately approved attempt; no application integration starts automatically.

RNL-002: exact cache contract

Cache the pure matrix product, then keep updating state. Keying one entry by the selected expert and every input bit preserved all 280 tested steps. Routing, activation and state updates still ran every time.

Using only the input as the key failed when state changed the selected expert. More cache hits did not make that shortcut correct. No latency comparison or process-memory benefit was tested in this trial.

Contract, counters and limits

The protocol was committed before execution. Twenty frozen trajectories used zero and nonzero initial states, including a repeated input that changes expert and signed-zero bit changes. Seven independent checks passed. The complete key matched the uncached reference's experts, scores, raw products, outputs and state bits on all 280 steps.

M avoided 138 matrix MACs but retained 7,560 router products, 840 activations and 840 state updates. It added 280 lookups, 437 input-bit comparisons and 260 expert comparisons. These are source-level counts, not CPU instructions or a speedup measurement.

On the second repeated [0,1,1] input from zero state, routing selected vision, whose product is [1,1,1]. The incomplete key reused coding's [1,1,2], producing a third state value of 0.675519824 instead of 0.60017854. That control diverged on 25 steps; its higher hit count is not a valid improvement.

The enabled entry measured 32 bytes by sizeof; VM objects measured 64 bytes with the entry versus 40 without it. These are not total process-memory measurements. The model was immutable and top-1, with fixed FP32 order and verified round-to-nearest/FTZ/DAZ controls. Exception flags, reloads, other models and general program equivalence were outside the contract.

Three supervised workers completed in a 1.281-second attempt, retaining about 629 kB including the derived summary. Resource limits and exits were verified; the elapsed attempt time is not an inference-latency comparison. No GPU, training, dependency installation or other Revia workload was used.

First experiment

FIRST-001 completed a bounded toy trial. Six independent checks passed: all three uncached representations matched bit-for-bit. The supplied cache changed recurrent behavior, so its skipped work cannot count as an equivalent speed improvement.

Smaller serialized files alone do not establish a useful Revia improvement. This toy result cannot establish language-model quality or predict savings for Qwen.

Sixteen case/state combinations covered zeros, repeats, changes, threshold boundaries and routing. An independent FP32 oracle checked full numeric trajectories, float bits, counters and complete containers. F/U/P each recorded 236 steps with no bit differences.

The authored cache had 126 hits and diverged from recomputed state on 123 of 236 steps. On the second repeated input from zero state, it retained 0.342717379 where recomputation produced 0.546377659. This is a change in recurrence semantics, not equivalent reuse.

Five interleaved batches per uncached representation used 100,000 steps each. Observed timing ranges overlapped. Load samples cover in-memory parsing only; disk-load latency, empty-worker RSS and empirical timer resolution remain unmeasured. Process peaks include instrumentation, transient parsing and evidence buffers. No speed or total-memory improvement is established.

The main attempt used 26 supervised launches, took 4.344 seconds and retained about 2.53 MB of evidence including its derived summary. What we know

The original ZIP was retained, hashed and safely inspected before reviewed CPU execution. Its handcrafted three-input, three-state, three-expert network remains a teaching prototype. The earlier C++ findings are now confirmed against original source.

Static findings and their evidence limits
  • The HTML matrix loop performs nine multiply-add iterations for a new event while its one-hot-input counter displays three. Routing, activation and state-update overhead are outside that counter.
  • The original loader expands nine packed matrix bytes to 27 one-byte indices, with all experts resident. Keeping nine packed bytes in RAM belongs to the new experimental P worker; neither number is total runtime memory.
  • The authored novelty cache skips state updates on repeated inputs even though routing and output depend on state. Its approximate threshold supplies no error bound.
  • Inspection uses E*(N+3)/4 instead of per-expert packing E*((N+3)/4). A 3-input, 1-state, 3-expert fixture measured four reported matrix bytes versus three actual payload bytes; its full file was 107 bytes.
  • The illustration honestly labels 113 full-file bytes versus 108 matrix-only FP32 bytes. These compare different scopes and do not prove total savings.
  • No tokenizer, learned weights, training loop, text inference or GGUF support is demonstrated. The supplied original checks lack full numeric trajectories; FIRST-001 now covers this toy's state, not language quality or VRAM.

Source hashes, full traces, raw timing batches and limits are retained in the reviewed experiment report and evidence summary. The original source was not patched; no research code was merged into Revia.

Related research and existing Revia evaluation paths

AQLM studies learned additive quantization. Switch Transformers studies sparse expert routing. They motivate questions; their results do not validate this prototype. QLoRA is a separate adapter-training approach, not an RNL result.

Reuse Revia's answer-quality gate, golden cases and offline-learning lineage and review rules when applicable. Their existing evidence retains its original scope.

Path into Revia

Keep useful ideas eligible for later integration. First reproduce the benefit against an unchanged baseline and record tradeoffs. Then review the held-out quality, safety and privacy results and propose a small change. Integration needs explicit authorization and a tested rollback; passing an experiment never merges or replaces a model automatically.

The broader RNL vision is a trainable adaptive/stateful architecture. Cache tests qualify one ingredient; their outcomes do not define or complete that architecture. Other workable approaches need their own evidence and evaluations.

Memory, corrections and future evaluated adapters remain a separate practical learning path. Any future training needs consent-aware data lineage and withdrawal checks. Deleting an example later does not erase its influence from trained weights.
