# STATE-020 — Loading only the parameters a conversation needs

13 November 2026. A small study with every script needed to repeat it.

The idea being tested: a model's parameters should not all have to be loaded. A small context comes in, slow signals pick the routes, and only the parts on those routes are needed.

**Result.** A small routed model that plans its route once at the start of each turn needed 26.7% of its parameters for a one-topic conversation and answered 100.0% on three seeds. An ordinary model the size of that loaded part, trained equally long, answered 63.8% (61.7–66.2). Choosing a route for every token, the usual mixture-of-experts way, scored lower and touched every expert, so nothing could stay unloaded.

It is a toy: under 2 million parameters, random facts, topics announced by cue words, turn starts given to the planner, and parameters counted as needed rather than actually unloaded. See "What this does not show".

## How to reproduce

**What you need**

- Python 3.12 and PyTorch 2.11 with CUDA (the study used `torch 2.11.0+cu128`). No other packages.
- One NVIDIA graphics card. The runs here used an RTX 5070 (12 GB) and an RTX 2070 SUPER (8 GB); a run took a few GB of VRAM.
- No data. The task is generated by the script from a fixed seed (`--data-seed 20261113`).

**The headline comparison (6 runs)**

```bash
for seed in 11 12 13; do
  python run_routes.py --arm turn --noise 0 --seed $seed --steps 24000 --log-every 2000 --device cuda:0 --out runs/long/turn-s$seed.json
  python run_routes.py --arm dense --experts 2 --seed $seed --steps 24000 --log-every 2000 --device cuda:0 --out runs/long/dense2-s$seed.json
done
python summarize.py runs/long
```

**Everything reported (59 runs)**

```bash
bash run_all.sh cuda:0 python
python summarize.py runs/main
python summarize.py runs/long
python summarize.py runs/scale
python measure_transfer.py --out runs/transfer.json
```

`run_all.sh` skips runs that are already finished, so it can be stopped and restarted. Run one at a time per card: runs sharing a card slowed each other to a fraction of their speed here.

**What you should see**

| Run | One-topic accuracy | Parameters loaded for a one-topic conversation |
|---|---|---|
| `--arm turn --noise 0`, 24,000 steps | 100.0% on seeds 11, 12, 13 | 26.7% |
| `--arm dense --experts 2`, 24,000 steps | 61.7%, 66.2%, 63.5% | all of a 0.50M model |
| `--arm turn --noise 0`, 6,000 steps | 88.3–92.6% | 26.7% |
| `--arm dense`, 6,000 steps | 90.1–100.0% | all of a 1.88M model |
| `--arm fast --noise 0`, 6,000 steps | 68.8–78.3% | 99.8% |

The summaries behind every table below are in `results/`. Seeds are fixed, but graphics cards do not compute identically, so expect the last digit to move; the ranges above are what three seeds gave here.

**How long**

About 4 minutes for a 6,000-step routed run and 17 minutes for a 24,000-step one on an RTX 5070 when it has the card to itself. The headline comparison is under an hour and a half; everything is several hours.

**Not included**

The per-run records and logs (one JSON and one log per run) are not in this folder; the scripts regenerate them.

## What was built

**The model.** A small transformer: width 128, 4 attention heads, 3 blocks. In each block the feed-forward part is split into a shared group of 64 units that is always on, and 16 "experts" of 128 units each. A routed model uses 2 experts per block at a time. An expert that is not on a route is never read, so it would not have to be loaded.

| | Parameters |
|---|---|
| Whole routed model | 1,884,848 |
| Always loaded (attention, word vectors, shared groups, the planner) | 305,840 (16.2%) |
| One expert | 32,896 (1.75%) |
| Loaded at any one moment (always-loaded part + 2 experts in each of 3 blocks) | 503,216 (26.7%) |

**The task.** 16 topics, each with its own facts about 2,048 entities: 8 attributes per entity, 64 possible values. Two of the eight attributes have the same value in every topic ("universal" facts); the other six differ by topic. That is 200,704 distinct random facts, 1.20 million bits. A conversation is 16 questions. Each turn opens with 3 of its topic's 4 cue words, then asks its questions: two tokens naming the entity, one naming the attribute, and the model must give the value. Chance is 1.6%.

The facts are random, so this measures how much a model can hold and recall. It does not measure reasoning or language.

Three kinds of conversation were scored, 2,048 conversations (32,768 questions) each:

| Conversation | What happens |
|---|---|
| One topic | All 16 questions on one topic |
| One switch | 8 questions on one topic, then 8 on another |
| Taking turns | 8 turns of 2 questions; each turn stays or moves to another topic at random |

**The versions** (`--arm`).

| Version | `--arm` | How the experts are used |
|---|---|---|
| Ordinary model | `dense` | No routing. Every unit is used for every token. Built at four sizes: 2, 4, 8 and 16 experts' worth per block (`--experts`) |
| Route planned once per turn | `turn` | A small planner reads only the turn's three opening words and picks 2 experts per block. The route is held until the next turn starts, so it is known before the turn is run |
| Route chosen every token | `fast` | Each block picks 2 experts for each token from the model's own state at that token. This is how mixture-of-experts models usually work |
| Route on a clock | `slow` | As above, but the choice is only renewed every 16 tokens and held in between |
| Route from a fading summary | `leaky` | The planner keeps a running summary of all words so far, each fading by 2% per token, and picks from that at every token. It is not told where turns start |
| Hand-made route | `oracle` | Not learned: topic number t always uses experts 2t and 2t+1 (wrapping round) in every block |

## How it was run

AdamW, learning rate 0.001 with 300 warm-up steps and a cosine fall to 5%, batch of 256 conversations, gradient clipping at 1.0. Every reported number is from seeds 11, 12 and 13 unless it says otherwise; a range in brackets is the lowest and highest of the three.

**Tuning, disclosed.** Settings were tried first on a separate seed (seed 1), which is not in any reported number. One thing was changed because of it: random noise added to the route choice during training (`--noise`), meant to make the router explore, was turned off. With it the once-per-turn router reached 53.5% on the pilot seed and without it 97.5%; the every-token router 50.0% and 91.9%. Reduced noise (0.3) gave 94.9%. The pilot seed scored higher than any of the three fresh seeds on the routed versions (97.5% against 88.3–92.6%), which is one reason only the fresh seeds are reported.

**A mistake in the first comparison, corrected.** The first set of runs trained every model for 6,000 steps. At that length the small ordinary model answered 32.2%, which made the routed model look far better than it is. Trained four times longer the small ordinary model reached 63.8%. All models are still climbing at 6,000 steps, so the 6,000-step table shows the order of the versions, and the 24,000-step table is the fair size-for-size comparison.

## Results

### 1. Same training length, 6,000 steps

"Topic facts" is accuracy on the six attributes that differ by topic. Universal facts were answered 99.9–100% by every version, including the smallest.

| Version | Whole model | Loaded for a one-topic conversation | Accuracy, one topic | Topic facts only |
|---|---|---|---|---|
| Ordinary, 16 experts' worth | 1.88M | 100% | 96.2% (90.1–100.0) | 94.9% (86.8–100.0) |
| Ordinary, 8 experts' worth | 1.09M | 100% | 67.8% (60.7–74.6) | 57.2% (47.6–66.2) |
| Ordinary, 4 experts' worth | 0.69M | 100% | 50.0% (48.4–51.6) | 33.4% (31.3–35.5) |
| Ordinary, 2 experts' worth | 0.50M | 100% | 32.2% (31.5–32.6) | 9.7% (8.8–10.3) |
| Route planned once per turn | 1.88M | 26.7% | 90.3% (88.3–92.6) | 87.1% (84.5–90.1) |
| Same, router's own weights never trained (`--freeze-router`) | 1.88M | 26.7% | 91.4% (88.2–95.8) | 88.6% (84.4–94.5) |
| Hand-made route | 1.88M | 26.4% | 84.7% (83.2–86.2) | 79.6% (77.7–81.7) |
| Route chosen every token | 1.88M | 99.8% | 72.8% (68.8–78.3) | 63.8% (58.5–71.1) |
| Route on a clock | 1.88M | 52.9% | 27.2% (27.1–27.3) | 3.0% (2.9–3.2) |
| Fixed random routes (`--fixed-routes`) | 1.91M | 27.8% | 32.2% (30.8–34.3) | 9.7% (7.9–12.5) |

Accuracy in one-switch and taking-turns conversations was within a point of the one-topic figure for every version except routing every token, which fell to 69.7% (64.8–77.8) when taking turns. After a topic change the once-per-turn router was right from the first question of the new topic (90.1% on question 1, 89.6–90.9% on questions 2 to 8).

At this training length the once-per-turn model, with 0.50M parameters loaded, scored what an ordinary model of about 1.68M would (read off the four ordinary sizes), 3.3 times its loaded size.

### 2. Trained four times longer, 24,000 steps

| Version | Loaded for a one-topic conversation | One topic | One switch | Taking turns |
|---|---|---|---|---|
| Ordinary, 0.50M (the size of the loaded part) | 0.50M, all of it | 63.8% (61.7–66.2) | 63.7% (61.4–66.5) | 63.2% (61.0–65.1) |
| Route planned once per turn, 1.88M | 0.50M, 26.7% of it | 100.0% | 100.0% | 100.0% |

All three seeds of the routed model reached 100.0% in all three kinds of conversation. On topic facts alone the small ordinary model answered 51.8% (49.1–55.0). The ordinary 1.88M model was not trained for 24,000 steps; at 6,000 it had already reached 100.0% on one seed.

### 3. What a conversation needs loaded

Route planned once per turn, 24,000 steps. "Experts touched" is how many of the 16 experts in a block a whole conversation used.

| Conversation | Experts touched per block | Share of the model that had to be loaded |
|---|---|---|
| One topic | 2.00 | 26.7% |
| One switch | 3.83 | 36.3% |
| Taking turns (up to 8 turns) | 6.11 (5.98–6.17) | 48.2% (47.5–48.5) |

If only a few experts are kept on the card and the rest are fetched when a route asks for them, this is how many experts were fetched per token, summed over the three blocks, after the first token:

| Conversation | Keeping 2 per block | Keeping 4 per block | Keeping 8 per block |
|---|---|---|---|
| One topic | 0 | 0 | 0 |
| One switch | 0.082 | 0.081 | 0.081 |
| Taking turns | 0.451 | 0.179 | 0.144 |

A topic change brings in about 5.5 new experts out of the 6 in use. In a one-topic conversation nothing is ever fetched after the start.

Routing every token is the opposite: it touched 15.96 of 16 experts per block in a single one-topic conversation, changed route at 96% of tokens, and would fetch 4.9 experts per token keeping 2 per block and still 2.6 keeping 8. Its routes followed the kind of token more than the topic. It saves arithmetic, not memory.

The routes of the once-per-turn model are not perfectly one-per-topic (a measure of how well the route follows the topic gave 0.76–0.84, where 1 is perfect), because different choices of three cue words for the same topic sometimes pick a different expert. That is why taking turns touches about 6 experts per block rather than the 4 two topics would need. There is room to load less in mixed conversations.

### 4. Twice the knowledge

32 topics (`--topics 32`), 397,312 facts (2.38 million bits), 12,000 steps.

| Version | Whole model | Loaded for a one-topic conversation | Accuracy, one topic | Topic facts only |
|---|---|---|---|---|
| Route planned once per turn, 32 experts (`--experts 32`) | 3.48M | 0.52M (14.9%) | 91.8% (88.4–94.3) | 89.2% (84.5–92.4) |
| Route planned once per turn, still 16 experts | 1.89M | 0.51M (27.0%) | 67.3% and 72.5% (seeds 12 and 13 only) | 56.4% and 63.4% |
| Ordinary, 16 experts' worth | 1.89M | 1.89M (100%) | 74.2% (71.3–79.9) | 65.6% (61.8–73.2) |
| Ordinary, 2 experts' worth | 0.50M | 0.50M (100%) | 32.3% (31.8–32.7) | 9.8% (9.2–10.5) |

With twice the experts the stored model doubled and what one conversation needs loaded did not grow: one switch needed 20.3% loaded and taking turns 27.4% (27.0–27.7). With the experts left at 16, accuracy fell: the knowledge has to be stored somewhere, even if little of it is loaded at a time.

Not run: an ordinary model of the full 3.48M. The 16-expert routed version has two seeds; its seed 11 run was stopped part-way.

### 5. Routing that failed

| Tried | Result | Why, as far as the runs show |
|---|---|---|
| Route chosen every token | 72.8% (68.8–78.3); 99.8% of the model needed per conversation | The route follows the token, not the topic, so every expert is used within a few tokens |
| Route on a 16-token clock | 27.2% (27.1–27.3); topic facts 3.0% | The clock ticks at places that have nothing to do with where the topic is announced. Turning the training noise off made no difference (pilot, 27.2% both ways) |
| Route from a fading summary of all words | 31.6% on the one pilot seed; 8.3 experts touched per block | The summary keeps moving, so the route keeps moving. One seed only, not rerun |
| Fixed random routes from the exact opening words | 32.2% (30.8–34.3) | The same topic got up to four different routes, one per choice of cue words, so each expert had to hold pieces of many topics |
| Random noise on the route choice during training | Once per turn 53.5% against 97.5% without; every token 50.0% against 91.9% (pilot seed) | The noise kept moving topics between experts while they were trying to learn them |
| Hand-made route by topic number | 84.7% (83.2–86.2), below the learned 90.3% | With 16 topics and 8 pairs of experts, two topics shared exactly the same experts in every block |

### 6. What the router actually learned

The router's own weights did not need training: left at their random start, the once-per-turn model scored 91.4% (88.2–95.8) against 90.3% (88.3–92.6) trained. But when the word vectors the planner reads were frozen as well, so that nothing about the route could change, accuracy fell to 32.2%.

So the learning that mattered was in the word vectors: training moved the cue words of one topic until they produced the same route. Put plainly, any stable assignment of topics to experts works; the hard part is recognising that two different openings belong to the same topic.

### 7. How fast the test PC can move parameters onto its cards

Copying 16-bit weights from RAM to each card, best of five, both cards idle (`measure_transfer.py`, `results/transfer.json`):

| Card | From ordinary memory | From page-locked memory | 256 MB takes | 1 GB takes |
|---|---|---|---|---|
| RTX 5070 | 6.4–7.3 GB/s | 12.4–13.4 GB/s | 19–36 ms | 75–141 ms |
| RTX 2070 SUPER | 5.4–5.9 GB/s | 6.1–6.2 GB/s | 41–43 ms | 161–171 ms |

Arithmetic only, not a measurement of a real model: if a 5 GB model split in the proportions of this toy, about 0.8 GB would always be loaded, a one-topic conversation would hold about 1.3 GB, and a topic change would bring in about 0.5 GB, which is roughly 36 ms on the 5070 and 78 ms on the 2070 SUPER. Copy speed is not the obstacle. Experts waiting in RAM save VRAM but not RAM; reading them from disk instead was not measured.

## What this does not show

- **Real language.** The facts are random and the topics are announced by dedicated cue words. Real conversations do not label their topic, and real knowledge does not split cleanly into topics.
- **Finding the signal.** The router that worked was told where each turn starts and reads only the opening words. Both routers that had to find the signal themselves failed. This is the main open problem.
- **A real model.** Under 2 million parameters, 3 blocks. Whether a large pretrained model can be split this way, and what it costs in quality, is untested.
- **Real paging.** Parameters were counted as needed or not needed. Nothing was actually unloaded, and no end-to-end speed was measured.
- **Training cost.** The routed model still has to be trained whole; only its use is cheaper.
- **Fully trained ordinary models.** The ordinary 0.50M model was still improving slowly at 24,000 steps and might rise further with a longer schedule. It has 0.50M parameters for 1.20 million bits of facts.
- **One task, one model shape, three seeds.** No confidence intervals beyond the range of three runs.
