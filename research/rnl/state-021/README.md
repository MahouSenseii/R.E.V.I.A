# STATE-021 — Finding the topic without being told

13 November 2026. A small study with every script needed to repeat it. It follows [STATE-020](../state-020/README.md).

STATE-020 showed that a small routed model can answer with about a quarter of its parameters loaded. But it was helped twice: every turn opened with cue words naming the topic, and the planner was told where each turn starts. Both routers that had to find the topic themselves failed there. This study takes the help away.

**Result.** With no cue words and no turn markers, a small planner that learns only by predicting the upcoming words found all 16 topics on every seed and was right as often as the information allows. The routed model then scored 97.7% with 37% of its parameters loaded for a one-topic conversation. A fully loaded ordinary model of the same size scored 97.5%. Conventional every-token routing reached 97.3% and 96.4% on two seeds and stalled at 68.8% on the third, with 99.9% of the model loaded each time. An ordinary model about the size of the loaded part scored 67.6%.

So the routed model does not answer better than a fully loaded one. What it changes is how much has to be loaded, and on these three seeds it trained more reliably than every-token routing.

It is still a toy: about 2 million parameters, random facts, and parameters counted as needed rather than actually unloaded. See "What this does not show".

## How to reproduce

**What you need**

- Python 3.12 and PyTorch 2.11 with CUDA (the study used `torch 2.11.0+cu128`). No other packages.
- One NVIDIA graphics card. The runs here used an RTX 5070 (12 GB) and an RTX 2070 SUPER (8 GB); a run took a few GB of VRAM.
- No data. The task is generated by the script from a fixed seed (`--data-seed 20261114`).

**The headline comparison (9 runs)**

```bash
for seed in 11 12 13; do
  python run_find.py --arm guess --seed $seed --steps 24000 --device cuda:0 --out runs/main/guess16-s$seed.json
  python run_find.py --arm dense --seed $seed --steps 24000 --device cuda:0 --out runs/main/dense16-s$seed.json
  python run_find.py --arm fast --seed $seed --steps 24000 --device cuda:0 --out runs/main/fast-s$seed.json
done
python summarize.py runs/main
python ceiling.py
```

**Everything reported**

```bash
bash run_all.sh cuda:0 python
python summarize.py runs/main
python summarize.py runs/pilot
```

`run_all.sh` skips runs that are already finished, so it can be stopped and restarted. Run one at a time per card.

**What you should see**

| Run | One topic | One switch | Taking turns | Loaded for a one-topic conversation |
|---|---|---|---|---|
| `--arm guess` (routed, planner finds the topic) | 97.6–97.7% | 95.3–95.6% | 81.8–82.2% | 36.4–36.7% |
| `--arm dense` (ordinary, everything loaded) | 97.5–97.6% | 95.2–95.3% | 83.3–84.1% | 100% |
| `--arm fast` (conventional every-token routing) | 97.3%, 68.8%, 96.4% | 95.0%, 68.6%, 93.2% | 82.6%, 68.3%, 82.8% | 99.9% |
| `--arm dense --experts 4` | 67.5–67.7% | 67.6–67.8% | 67.6–67.9% | 100% of a 0.74M model |
| `--arm dense --experts 2` | 60.9–61.4% | 60.8–61.9% | 60.4–62.0% | 100% of a 0.55M model |

`ceiling.py` should print 67.4%, 96.9%, 99.7% and 100.0% as the best possible answer on questions 1 to 4. The planner line in each `guess` log should read "16 of 16 guesses in use, standing for 16 of 16 topics". Seeds are fixed, but graphics cards do not compute identically, so expect the last digit to move.

**How long**

About 12 minutes for a 24,000-step run on an RTX 5070 when it has the card to itself, and about 20 on an RTX 2070 SUPER. The planner is trained first inside each `guess` run and takes about a minute.

**Not included**

The per-run records and logs are not in this folder; the scripts regenerate them.

## What was built

**The task.** 16 topics. A name is two syllables. There are 512 first syllables and each topic uses 32 of them, picked at random, so a syllable belongs to one topic, to several, or to none. A conversation is 16 questions (first syllable, second syllable, attribute, and the model must give the value) and nothing else: no cue words, no markers. The same name has different values in different topics, so the topic has to be worked out from the names asked about so far, and it can change without notice. 196,608 random facts, 1.18 million bits.

A name fits 1.88 topics on average, and 42% of names fit only one. That sets a limit no reader can beat: a reader who knows every fact but not the topic can be right on 67.4% of first questions, 96.9% of second questions, 99.7% of third and 100% from the fourth (`ceiling.py`).

**The model.** As in STATE-020: a small transformer (width 128, 4 heads, 3 blocks) whose feed-forward part is, per block, a shared group of 64 units that is always on plus 16 experts of 128 units, 2 in use.

| | Parameters |
|---|---|
| Whole routed model, with its planner | 2,005,488 |
| The planner | 77,680 |
| Always loaded (attention, word vectors, shared groups, the planner) | 426,480 (21.3%) |
| One expert | 32,896 |
| Loaded at any one moment | 623,856 (31.1%) |
| Ordinary models: 16, 4 and 2 experts' worth | 1,927,808 · 743,552 · 546,176 |

**The versions** (`--arm`).

| Version | `--arm` | How the experts are chosen |
|---|---|---|
| Ordinary model | `dense` | No routing. Every unit is used for every token |
| Planner's guess | `guess` | A small separate reader (a GRU of 64 units) reads the tokens and keeps a guess, one of 16 numbers, about what is being talked about. It is trained first, alone, to predict the next 8 tokens through that guess only: each guess has its own list of how likely every token is. It never sees a topic label or an answer. It is then left unchanged, and the route is a fixed function of its guess |
| Every token | `fast` | Each block picks 2 experts for each token from the model's own state. This is how mixture-of-experts models usually work |
| Running average | `sum` | Experts are picked at every token from an average of the words so far in which each word fades; trained only through the answers |
| Told the topic | `oracle` | The route is a fixed function of the true topic. An upper bound, not a method |

Three kinds of conversation were scored, 2,048 conversations each: one topic throughout; one unannounced switch after 8 questions; and two topics taking turns every 2 questions.

## How it was run

AdamW, learning rate 0.001 with 300 warm-up steps and a cosine fall to 5%, batch of 256 conversations, gradient clipping at 1.0, 24,000 steps. Reported numbers are from seeds 11, 12 and 13 unless they say otherwise; a range is the lowest and highest of the three.

**Tuning, disclosed.** Settings were tried on a separate seed (seed 1) at half length (12,000 steps), and the planner's own settings were tried on the planner alone. Those pilot results are listed separately below and are not in any three-seed number.

**A pilot reading that did not hold.** At half length the routed model was ahead of the fully loaded ordinary model (97.7% against 95.7%), and every-token routing looked like a failure (69%). With full training the first two tie, and every-token routing reached 96–97% on two of its three seeds. Only the full-length runs should be compared.

## Results

### 1. Three seeds, 24,000 steps

| Version | Size | Loaded: one topic / one switch / taking turns | One topic | One switch | Taking turns |
|---|---|---|---|---|---|
| Routed, planner finds the topic | 2.01M | 36.6% / 47.9% / 60.9% | 97.7% (97.6–97.7) | 95.4% (95.3–95.6) | 82.0% (81.8–82.2) |
| Ordinary, everything loaded | 1.93M | 100% | 97.5% (97.5–97.6) | 95.3% (95.2–95.3) | 83.6% (83.3–84.1) |
| Routed, planner given 32 guesses and a weak push | 2.02M | 36.5% / 47.7% / 60.9% | 97.6% (97.6–97.7) | 95.2% (95.1–95.3) | 81.4% (81.1–81.5) |
| Routed, route chosen every token | 1.93M | 99.9% | 87.5% (68.8–97.3) | 85.6% (68.6–95.0) | 77.9% (68.3–82.8) |

| Ordinary, 4 experts' worth | 0.74M | 100% | 67.6% (67.5–67.7) | 67.7% (67.6–67.8) | 67.7% (67.6–67.9) |
| Ordinary, 2 experts' worth | 0.55M | 100% | 61.1% (60.9–61.4) | 61.2% (60.8–61.9) | 61.3% (60.4–62.0) |

The routed model with the planner ties the fully loaded ordinary model on one topic and one switch. When the topic changes every two questions the ordinary model is 1.6 points ahead, and the routed model needs 61% of its parameters.

Given 32 guesses and only a weak push to use them (`--guesses 32 --even 0.1`), the planner settled on 16 of them on all three seeds and scored the same as with 16, so it does not have to be told how many topics there are.

Every-token routing was uneven: seeds 11 and 13 reached 97.3% and 96.4% on one topic, while seed 12 stayed at 68.8%, the level of a reader that ignores the rest of the conversation. In all three a single conversation touched 15.98 of the 16 experts in every block, and the route changed at 96% of tokens.

## What failed or did not help

| Tried | Result |
|---|---|
| Conventional every-token routing as a way to load less | Two seeds reached 96–97% and one stalled at 68.8%. In every case a conversation touches every expert, so nothing can stay unloaded |
| A running average of the words, trained only through the answers | 66% and 76% at half length with 75–83% loaded (one seed, not rerun at full length) |
| A planner with no push to use all its guesses, or with too few | Collapsed to one guess, or merged topics in pairs |
| A planner with twice as many guesses as topics and a strong push | Split every topic in two: 95.9% with 45% loaded (pilot) |
| Switching on the second guess's experts while the planner is unsure | No gain and more experts in use. The uncertainty is in the question, not in what is loaded |
| Reading the half-length pilot as "routed beats fully loaded" | They tie at full length |

## What this does not show

- **Real language.** The facts are random and the topics are sets of syllables. Real text does not come in 16 clean topics.
- **Better answers.** The routed model ties a fully loaded model of the same size. It does not beat it, and when the topic changes every two questions it is slightly behind.
- **Real paging.** Parameters were counted as needed or not needed. Nothing was actually unloaded, and no speed was measured.
- **A robust planner.** With no push it collapses to one guess, and with spare guesses and a strong push it splits topics. Spare guesses with a weak push worked on three seeds. The strong-push variant and the running-average router rest on one pilot seed at half length.
- **Frequent topic changes.** With a change every two questions the loaded share rises to 61%.
- **One task, one model shape, three seeds.**
