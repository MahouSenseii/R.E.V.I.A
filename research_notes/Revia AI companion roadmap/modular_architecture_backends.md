# Modular Architecture, Pluggable LLM Backends, Tool/Plugin Protocols and Coding Assistance for Revia (research as of late Sept 2026)

Scope: how a solo developer can turn Revia (Windows 11, C++20, Qt 6, MinGW, currently hard-wired to llama.cpp `llama-server` + Qwen) into a modular companion with swappable local/cloud backends, a skill/plugin system on standard tool protocols, and strong coding assistance. Local-first by default, cloud optional.

Local codebase context (from reading the repo, not the web): `Public/LLM/llmService.h` holds a concrete `llamaCppService llamaCpp;` member plus an `llmBackendType backendType` enum, and exposes task-specific methods (`GenerateResponse`, `GenerateCodeReview`, `AnalyzeImage`, `SummarizeConversation`, `EvaluateMemory`, `GenerateComputerSubgoal`, `EmbedMemory`, etc.) with `std::stop_token` cancellation and a `DeltaHandler` streaming callback. Backend-specific code lives under `Public/LLM/LLamaCPP/` (`llamaCppService.h`, `llamaCppServerProcess.h`, `llamaCppEmbeddingService.h`). Recent commits added exact token counting through llama-server `/tokenize` and history compaction. These task methods are natural routing keys for a per-task model router.

## 1. Pluggable LLM backends: lingua franca APIs, backend differences, C++ provider interface, per-task routing with privacy

### Takeaway
There is no single wire format that covers everything: OpenAI-style Chat Completions is still the widest common denominator (every local server speaks it), the Anthropic Messages API has become a second de facto local standard (llama.cpp, Ollama and LM Studio all now serve `/v1/messages`), and "Open Responses" is an emerging multi-provider spec. Compatibility layers silently drop features (caching, strict schemas, reasoning controls), so Revia should own a canonical internal message/event model and write two or three thin adapters (OpenAI Chat, Anthropic Messages, optionally Responses/Gemini-native), rather than embedding a Python gateway such as LiteLLM.

### Cited Findings

**llama.cpp `llama-server` (current backend) now exposes three API dialects plus management endpoints**
- Endpoints: `/v1/chat/completions` (streaming), `/v1/completions`, `/completion` (native), `/v1/responses` (OpenAI Responses API), `/v1/embeddings`, `/embedding`, `/reranking` (`/rerank`, `/v1/rerank`), `/health`, `/tokenize`, `/detokenize`, `/apply-template`, `/v1/models`, `/props`, `/slots`, `/metrics` (needs `--metrics`), `/lora-adapters`, and `/slots/{id}?action=save|restore|erase` for KV-cache persistence — [llama.cpp server README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)
- llama-server also supports the Anthropic Messages API, so Claude-compatible clients can run against local models — [Hugging Face blog: New in llama.cpp: Anthropic Messages API](https://huggingface.co/blog/ggml-org/anthropic-messages-api-in-llamacpp)
- Tool calling requires `--jinja` and may need `--chat-template-file` to get a tool-capable template; native tool-call styles are detected per model, with a generic fallback style — [llama.cpp server README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md); [llama.cpp function-calling docs](https://github.com/ggml-org/llama.cpp/blob/master/docs/function-calling.md)
- Structured output: `response_format` supports plain JSON and schema-constrained JSON; grammar sampling via `--grammar` / `--json-schema` — [llama.cpp server README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)
- Reasoning controls: `--reasoning-format` (none / deepseek / deepseek-legacy), a `reasoning_budget`, `enable_thinking` passed through `chat_template_kwargs`; multimodal (image/audio/video) needs `--mmproj`; `file://` media needs `--media-path` — [llama.cpp server README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)
- Router/multi-model mode: `--models-dir`, `--models-max`, `--models-autoload`, and `?model=` routing; README also lists built-in tools (`--tools`) and MCP server configuration (`--mcp-servers-config`, `--mcp-servers-json`) — [llama.cpp server README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md) (note: these came from a summarized fetch of the README; verify exact flag names against the build Revia pins)
- Prompt caching: `cache_prompt` (default on), `--cache-reuse` (KV shifting), slot save/restore; streaming is SSE — [llama.cpp server README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)

**Other local servers**
- Ollama supports a subset of the Anthropic Messages API (set `ANTHROPIC_BASE_URL`, e.g. to run Claude Code against open models); tool-choice controls, deferred tools and hosted web search are not fully supported — [Ollama docs: Anthropic compatibility](https://docs.ollama.com/api/anthropic-compatibility)
- Ollama also has (historically "experimental") OpenAI API compatibility — [Ollama OpenAI compatibility docs](https://ollama.readthedocs.io/en/openai/) (older docs mirror; check current docs.ollama.com)
- LM Studio serves OpenAI-compatible endpoints, Anthropic-compatible endpoints (`POST /v1/messages`, added in 0.4.1), and its own REST API; it ships a CLI (`lms`) and a headless daemon `llmster` for GUI-less service use — [LM Studio REST API docs](https://lmstudio.ai/docs/developer/rest); [LM Studio Anthropic compat](https://lmstudio.ai/docs/developer/anthropic-compat); [LM Studio headless](https://lmstudio.ai/docs/developer/core/headless)
- vLLM does not officially support Windows (WSL2 is the recommended path); a community fork (SystemPanic/vllm-windows v0.20.0, April 30 2026) ships native Windows wheels — [fazm.ai: vLLM on Windows in 2026](https://fazm.ai/t/vllm-windows-support-2026); [dasroot: run vLLM natively on Windows](https://dasroot.net/posts/2026/05/run-vllm-natively-windows-without-wsl/) (secondary sources)
- SGLang on Windows likewise relies on WSL2 (e.g. Unsloth Studio installs WSL2 to run vLLM/SGLang) — [unsloth PR #12024](https://github.com/unslothai/unsloth/pull/12024)
- TabbyAPI is the official OpenAI-compatible server for ExLlamaV3 (EXL3 quantization, based on QTIP; 2–8-bit KV-cache quantization; HF Jinja2 chat templates) — [turboderp-org/exllamav3](https://github.com/turboderp-org/exllamav3); [exllamav3 on PyPI](https://pypi.org/project/exllamav3/)

**Cloud providers: compatibility layers drop features**
- Anthropic's OpenAI-SDK compatibility layer is "primarily intended to test and compare model capabilities, and is not considered a long-term or production-ready solution"; limitations: `strict` on tools is ignored (no schema guarantee), `response_format` ignored, prompt caching not supported, audio stripped, `reasoning_effort`/`logprobs`/`seed` ignored, temperature capped at 1, `n` must be 1, system/developer messages hoisted and concatenated into one initial system message, thinking can be enabled via `extra_body` but the thought text is not returned, `usage.*_details` always empty — [Anthropic docs: OpenAI SDK compatibility](https://platform.claude.com/docs/en/api/openai-sdk)
- Same page: on current Claude models thinking is adaptive and on Claude 5 models it is on by default; manually configured budgeted thinking is "a legacy mode"; for PDFs, citations, thinking and prompt caching use the native Messages API — [Anthropic docs: OpenAI SDK compatibility](https://platform.claude.com/docs/en/api/openai-sdk)
- Anthropic native: `POST /v1/messages/count_tokens` counts input tokens (same model/system/messages/tools) without generating and is free; prompt caching is explicit via `cache_control` breakpoints (up to 4), covering tools → system → messages in that order; 5-minute default TTL with a paid 1-hour option; cache reads ~10% of input price, writes ~25% more — [Claude prompt caching docs](https://platform.claude.com/docs/en/build-with-claude/prompt-caching); pricing/TTL detail via [hidekazu-konishi guide](https://hidekazu-konishi.com/entry/anthropic_claude_api_prompt_caching_and_token_efficiency.html) (secondary)
- Gemini's OpenAI-compatible endpoint maps `reasoning_effort` low/medium/high to 1K/8K/24K thinking-token budgets; finer control via `extra_body.google.thinking_config`; `reasoning_effort` and `thinking_level`/`thinking_budget` cannot be combined — [Gemini API: OpenAI compatibility](https://ai.google.dev/gemini-api/docs/openai)
- Real-world breakage: users report Gemini 3 preview rejecting `reasoning_effort: "medium"` and Gemini 3 Flash rejecting `"minimal"` through the OpenAI-compat endpoint despite docs — [Google AI dev forum thread 1](https://discuss.ai.google.dev/t/gemini-3-preview-openai-compatible-rejects-reasoning-effort-medium-works-with-low-and-high/112648); [thread 2](https://discuss.ai.google.dev/t/openai-compat-api-rejects-reasoning-effort-minimal-for-gemini-3-flash/118724)

**Emerging standard: Open Responses**
- Open Responses is an open spec "inspired by the OpenAI Responses API" defining a shared request/response model, semantic streaming events (not raw text deltas), tool invocation patterns, and extension points for provider-specific item types; a dated spec version 2026-04-24 exists — [openresponses.org](https://www.openresponses.org/); [spec 2026-04-24](https://www.openresponses.org/specification/2026-04-24); [GitHub openresponses/openresponses](https://github.com/openresponses/openresponses)
- Announced Jan 2026 with support from OpenRouter, Ollama, Hugging Face, vLLM and others — [AINews / smol.ai, 2026-01-15](https://news.smol.ai/issues/26-01-15-openresponses/); [OpenAI dev community announcement](https://community.openai.com/t/open-responses-for-the-open-source-community/1371770)

**Gateways**
- LiteLLM (Python) normalizes 100+ providers and has per-provider docs (e.g. Gemini thinking mapping) — [LiteLLM Gemini provider docs](https://docs.litellm.ai/docs/providers/gemini)
- Supply-chain warning: on 2026-03-24 malicious `litellm` 1.82.7 and 1.82.8 were uploaded directly to PyPI (no matching GitHub tag) with a `.pth` file that ran on every Python start and stole SSH keys/cloud credentials; live ~40 minutes, >119k downloads; part of the "TeamPCP" campaign that also hit Trivy, npm and Checkmarx KICS — [LiteLLM security update](https://docs.litellm.ai/blog/security-update-march-2026); [PyPI incident report](https://blog.pypi.org/posts/2026-04-02-incident-report-litellm-telnyx-supply-chain-attack/); [Datadog Security Labs](https://securitylabs.datadoghq.com/articles/litellm-compromised-pypi-teampcp-supply-chain-campaign/)

### Inferences
- **Two adapters cover almost everything.** An `OpenAIChatAdapter` reaches llama-server, Ollama, LM Studio, vLLM/SGLang (via WSL2), TabbyAPI, KoboldCpp, OpenRouter, Gemini-compat, xAI and Mistral (the last few are OpenAI-compatible per common practice; not re-verified here). An `AnthropicMessagesAdapter` reaches Claude natively and also llama-server/Ollama/LM Studio locally. Because Anthropic's own OpenAI-compat layer drops caching, strict tools and thinking text, a native Messages adapter is required for a serious cloud Claude backend. Add an `OpenResponsesAdapter` later, once Open Responses support settles; it is the most likely future lingua franca for agentic streaming.
- **Proposed C++20 provider interface (sketch):**
  - `struct ProviderCaps { bool tools, parallelTools, strictSchema, jsonSchema, grammar, vision, audio, reasoningControl, reasoningText, promptCacheExplicit, promptCacheAuto, tokenizeEndpoint, countTokensEndpoint, embeddings, rerank; int maxContext; }`: discovered at startup (llama-server `/props`, `/v1/models`), overridable in config.
  - Canonical request: `ChatRequest { std::vector<Msg> msgs; std::vector<ToolSpec> tools; ToolChoice; std::optional<JsonSchema> output; Reasoning {effort | budget | off}; CacheHints; Sampling; int maxTokens; }` where `Msg` holds `std::vector<Part>` and `Part = std::variant<Text, Image, ToolCall, ToolResult, Thinking>`.
  - Streaming: `using Event = std::variant<TextDelta, ReasoningDelta, ToolCallDelta, ToolCallDone, Usage, Stop, Error>;` delivered through a callback or a Qt signal. This generalizes Revia's existing `DeltaHandler(const std::string&)`.
  - `class IChatProvider { virtual ProviderCaps caps() = 0; virtual Result<Response> chat(const ChatRequest&, EventSink, std::stop_token) = 0; virtual Result<int> countTokens(const ChatRequest&) = 0; virtual Result<Embedding> embed(...) = 0; }`. Keep token counting per-provider: llama-server `/tokenize` (already used), Anthropic `count_tokens`, otherwise an estimate.
  - Each adapter degrades gracefully. If `strictSchema` is false, validate the JSON client-side and retry. If `grammar` is true (llama.cpp), use GBNF/JSON-schema constrained decoding for Revia's structured calls (`GenerateCodeReview`, `EvaluateMemory`, `GenerateComputerSubgoal` all take schemas).
- **Refactor path for Revia:** turn `llmService` into a facade over an `IChatProvider` registry plus a `Router`. Keep the task methods; each maps to a named *route* (e.g. `chat.persona`, `memory.evaluate`, `code.review`, `vision.analyze`, `summarize`, `embed`) configured in JSON/TOML: `{route → provider, model, reasoning, maxTokens, privacyTier}`. `llamaCppServerProcess` stays as an optional "managed local backend" (process lifecycle), separate from the HTTP adapter.
- **Privacy controls:** tag each route and each message with a tier. `LocalOnly` covers memory, private profile, screen captures and anything under `PrivateMemoryAccess`. `CloudAllowed` requires user opt-in per route. `CloudRedacted` strips memory snippets and file paths before sending. Enforce the tier in the router, not the adapter. Show a visible indicator when a turn leaves the machine. Default config: all routes local; cloud keys stored with Windows DPAPI/Credential Manager (inference, not researched).
- **Prompt-cache friendliness:** keep system prompt, persona and tool list byte-stable and ordered first so that llama.cpp `cache_prompt`, Anthropic `cache_control` breakpoints, and automatic caching on other providers all hit. MCP 2026-07-28 even asks servers to return tools in deterministic order for this reason (see section 3).
- **Avoid a bundled Python gateway by default.** LiteLLM is useful but adds a Python runtime and a demonstrated supply-chain risk. If Revia ever uses it, run it as an optional sidecar with pinned, hash-locked versions.

### Gaps
- Did not verify current xAI, Mistral, OpenRouter and KoboldCpp API specifics (tool-call formats, caching, reasoning params) for 2026. Treat their OpenAI compatibility as likely but unverified.
- Did not fetch OpenAI's own current docs on Responses vs Chat Completions, automatic prompt caching thresholds, or structured-output limits.
- The llama-server `--tools` / `--mcp-servers-*` flags and `/v1/chat/completions/control` came from an LLM-summarized README fetch. Verify them against the pinned llama.cpp build.
- No authoritative source found for a maintained C++ SDK of any LLM provider. C++ adapters will be hand-written over Qt networking.

## 2. Best local models (2026) for a 12 GB + 8 GB GPU setup; quantization, speculative decoding, multi-GPU

### Takeaway
As of Sept 2026 the Qwen 3.6/3.8 generation and Google's Gemma 4 dominate local use. 20 GB of total VRAM fits a ~27B dense model at ~4-bit (coding/reasoning), or a 35B-A3B MoE with some experts offloaded to system RAM (fast chat). A small 4–9B model can live on the 8 GB card for fast side tasks. llama.cpp now has native multi-token-prediction (MTP) speculative decoding for Qwen3.6, a cheap ~1.4–2x generation speedup.

- Qwen3.5 small series (released 2026-03-02): 0.8B, 2B, 4B, 9B. They are dense, natively multimodal (vision encoder), support thinking and non-thinking modes, and are Apache-licensed. 0.8B/2B target edge/low latency, 9B is the reasoning flagship of the small series — [MarkTechPost](https://www.marktechpost.com/2026/03/02/alibaba-just-released-qwen-3-5-small-models-a-family-of-0-8b-to-9b-parameters-built-for-on-device-applications/); [Artificial Analysis](https://artificialanalysis.ai/articles/qwen3-5-small-models); [Qwen on X](https://x.com/Alibaba_Qwen/status/2028460046510965160)

### Inferences
- **Suggested 12 GB + 8 GB layout** (numbers derived from the cited VRAM figures):
  - *Main companion (chat/persona + vision):* Qwen3.6-35B-A3B at UD-Q3/Q4 split across both cards. At 4-bit it needs ~23 GB, so offload some MoE expert tensors to system RAM (llama.cpp `-ot`/`--n-cpu-moe`-style expert offload; exact flag not verified here). With only 3B active parameters it stays fast even when partly on CPU. Alternative: Gemma 4 26B A4B (similar MoE profile, strong Tau2 tool-use scores), or Gemma 4 12B fully on the 12 GB card if audio input is wanted.
  - *Coding / hard reasoning, local:* Qwen3.8-27B (or Qwen3.6-27B) at Q4 (~16.8 GB file) split `--tensor-split 12,8`-style across both GPUs with a quantized KV cache. Add MTP for speed. Context will be limited to tens of thousands of tokens at this VRAM, and a 27B dense model cannot co-reside with the 35B MoE, so swap via llama-server router mode (`--models-max 1`, autoload) or route coding to cloud.
  - *Fast side model on the 8 GB card:* Qwen3.5-4B/9B or Gemma 4 E4B for memory evaluation, summarization, intent classification, curiosity planning, embeddings/rerank, and as a routing/guard model. This lets background tasks (Revia's summarizer, memory evaluation) run concurrently without evicting the main model's KV cache.
- Revia's existing model (Qwen) and llama-server setup mean the Qwen3.6/3.8 upgrade is mostly a GGUF swap plus template/sampler settings. The main breaking concern is thinking-on-by-default: use `enable_thinking:false` for persona chat and reserve thinking for `deepReasoning`.
- GGUF + llama.cpp stays the right default on Windows/MinGW (native, CUDA/Vulkan builds, router mode, MTP). EXL3/TabbyAPI and vLLM/SGLang are optional power-user backends reachable through the same OpenAI adapter. vLLM and SGLang effectively require WSL2 on Windows.

## 3. Tool and plugin protocols: MCP (spec, transports, C++), ecosystem, security; A2A; OpenAI Apps SDK / MCP Apps; plugin architectures in open-source assistants; skill manifests, permissions and sandboxing

### Takeaway
MCP is the de facto tool protocol. Its 2026-07-28 revision made the core stateless (no `initialize` handshake, no sessions), which makes writing a small C++/Qt client much easier. No official C++ SDK exists (official Tier-1 SDKs: TypeScript, Python, Go, C#), and community C++ SDKs lag the spec. Revia should host its own MCP client (stdio via QProcess + Streamable HTTP via QNetworkAccessManager), treat every tool description and result as untrusted input, and wrap MCP servers in its own manifest/permission layer. A2A matters only if Revia later delegates to remote agents.

### Cited Findings

**MCP spec status**
- Current spec: **2026-07-28** (previous: 2025-11-25). Major changes: protocol-level sessions and `Mcp-Session-Id` removed from Streamable HTTP; `initialize`/`initialized` handshake removed, and every request now carries protocol version and client capabilities in `_meta` (SEP-2575); new required `server/discover` RPC; `subscriptions/listen` replaces the HTTP GET stream and `resources/subscribe`; `ping` and `logging/setLevel` removed; Tasks moved to an official extension (`io.modelcontextprotocol/tasks`, SEP-2663); Multi Round-Trip Requests (`resultType: "input_required"`) replace server-initiated sampling/elicitation/roots requests (SEP-2322); SSE resumability (`Last-Event-ID`) removed — [MCP 2026-07-28 changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)
- Minor: `Mcp-Method`/`Mcp-Name` headers required on Streamable HTTP POSTs (SEP-2243); `ttlMs`/`cacheScope` on list results (SEP-2549); servers SHOULD return `tools/list` in deterministic order "to improve LLM prompt cache hit rates"; JSON Schema 2020-12 allowed in `inputSchema`/`outputSchema` (SEP-2106); OAuth hardening (RFC 9207 `iss` validation SEP-2468, issuer-bound credentials SEP-2352); W3C trace context in `_meta` (SEP-414) — [MCP changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)
- Deprecated: Roots, Sampling and Logging features (SEP-2577; migrate to tool params, direct LLM calls, stderr/OpenTelemetry); HTTP+SSE transport; Dynamic Client Registration (in favor of Client ID Metadata Documents). Minimum 12-month deprecation window — [MCP changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)
- Release blog: stateless core means "any request can land on any instance behind a plain round-robin load balancer"; the Extensions framework formally includes Tasks, MCP Apps and Enterprise Managed Authorization; **Tier-1 SDKs supporting 2026-07-28: TypeScript, Python, Go, C#; Rust in beta** (no C++ SDK mentioned) — [MCP blog: The 2026-07-28 Specification](https://blog.modelcontextprotocol.io/posts/2026-07-28/)

### Inferences
- **Implement the MCP client in-house with Qt.** The protocol is JSON-RPC 2.0. stdio maps to `QProcess` with newline-delimited JSON on stdin/stdout (stderr for logs). Streamable HTTP maps to `QNetworkAccessManager` POST with an SSE-or-JSON response. The 2026-07-28 stateless core removes session bookkeeping. Support both dialects: probe `server/discover`, and fall back to the 2025-11-25 `initialize` handshake plus `Mcp-Session-Id`, since most ecosystem servers (OBS, HA, Playwright) will lag for months. Skip deprecated Sampling/Roots/Logging. Community C++ SDKs are either behind the spec or heavy; MinGW compatibility of gopher-mcp is unverified.
- **Revia "skill" = manifest + one of three runtimes:** (a) an MCP server (stdio child process or HTTP), (b) a built-in C++ skill, (c) an out-of-process sidecar speaking MCP. Manifest fields: `id`, `version`, `publisher`, `runtime` (command/url), `tools` (allow-list with pinned description hashes), `permissions` (fs paths r/w, network hosts, process spawn, screen/mic/camera, clipboard, home-automation domains), `confirmation` policy per tool (auto / ask / always-ask for destructive), `privacyTier`, and `autostart`. This follows SillyTavern (manifest.json), OVOS (skill.json) and HA (registered LLM API) precedents, but adds the permission model those lack.
- **Mitigations dictated by the security findings:**
  - Never auto-launch MCP servers from project/repo config files; this is the CSA-documented IDE failure mode.
  - Pin and diff tool descriptions (hash on first approval, re-prompt on change) to blunt tool poisoning and "rug pulls".
  - Keep untrusted tool output (web pages, Playwright snapshots, files) in clearly delimited data blocks, and never let it trigger privileged tools without user confirmation.
  - Enforce least privilege per skill by running stdio servers under a restricted token/AppContainer and a job object (Windows mechanisms; see section 4 on Codex's Windows sandbox for a reference design).
  - Keep an audit log of every tool call. Revia already has an approval flow ("pending approval" in commit history) to build on.
- **MCP Apps** could later let skills render UI inside Revia's Qt window via a sandboxed web view (QtWebEngine). This is optional and low priority for a companion.
- **A2A** is only worth adding if Revia should delegate to or be called by remote agents. For a local companion, MCP (tools) plus ACP (coding agents, section 4) cover the needs.

- MCP Registry (official server registry) status in 2026 not researched.

## 4. Coding assistance: how the major agents work; integrate (CLI agent / ACP / MCP / LSP / IDE) vs build; local vs cloud coding models; safe code execution

### Takeaway
The pragmatic path is to **drive existing agents rather than build one**. The Agent Client Protocol (ACP) lets one client (Revia) host Claude Code, Codex, Gemini CLI and others over JSON-RPC. Codex also exposes a stable JSON-RPC "app-server" over stdio, and Claude Code offers headless stream-json and an Agent SDK. Revia's own coding features (code review, explanations) can stay on local Qwen models, with heavy agentic work routed to a cloud-backed agent. Code execution must run inside an OS sandbox; Codex's Windows sandbox (restricted tokens + ACLs + sandbox users/firewall) is a documented reference design.

### Cited Findings

**How the agents work**
- Aider: builds a repository map by parsing files with tree-sitter to extract definitions/references, then ranks symbols with a PageRank-style graph to fit a token budget — [Aider: Building a better repository map with tree sitter (2023, older but still the design)](https://aider.chat/2023/10/22/repomap.html)
- Aider edit formats: `whole`, `diff` (search/replace blocks), `udiff`, and `architect` (a strong reasoning model plans, a cheaper editor model applies edits); the format is matched to model capability. Git-first: each edit becomes a commit — [Aider docs](https://aider.chat/docs/); [Agent Patterns Catalog: Aider](https://www.agentpatternscatalog.org/compositions/aider/) (secondary); [pinggy comparison](https://pinggy.io/blog/best_open_source_cli_coding_agents/)
- OpenHands targets autonomous unattended runs (browse, edit, test, retry); Cline runs in VS Code/JetBrains/Cursor/Windsurf plus CLI with any OpenAI-compatible or local (Ollama/LM Studio) model; Continue is provider-agnostic with local-model support — [pinggy: best open-source CLI coding agents 2026](https://pinggy.io/blog/best_open_source_cli_coding_agents/); [morphllm comparison](https://www.morphllm.com/ai-coding-assistant-open-source) (secondary)
- Reported GitHub stars (mid-2026): Codex CLI ~119k, Pi ~98k, OpenHands ~85k, Cline ~67k, Aider ~48k. Licenses: OpenHands MIT; Aider, Goose, Cline, Continue, Codex, Qwen Code Apache-2.0 — [morphllm](https://www.morphllm.com/ai-coding-assistant-open-source); [pinggy](https://pinggy.io/blog/best_open_source_cli_coding_agents/) (secondary; not verified against GitHub)

**Integration surfaces**
- **Agent Client Protocol (ACP, Zed):** an open standard so any editor/client can host any ACP agent. The Claude Code adapter wraps Claude Code's SDK and translates it into ACP JSON-RPC (Apache-licensed, npm `@zed-industries/claude-code-acp`). `codex-acp` is a Rust binary distributed via npm with native Windows/macOS/Linux builds. Zed runs Codex, Claude Agent, Gemini CLI and other ACP agents concurrently — [Zed ACP](https://zed.dev/acp); [agentclientprotocol.com agents list](https://agentclientprotocol.com/get-started/agents); [Zed blog: Claude Code via ACP](https://zed.dev/blog/claude-code-via-acp); [zed-industries/codex-acp](https://github.com/zed-industries/codex-acp)
- **Codex app-server:** a long-lived Rust process with bidirectional JSON-RPC 2.0 that powers the Codex web app, desktop app, VS Code extension and CLI. Transports: stdio JSONL (stable) or WebSocket/Unix socket via `--listen`. Third-party clients exist in Go, Python, TS, Swift and Kotlin — [OpenAI: Unlocking the Codex harness](https://openai.com/index/unlocking-the-codex-harness/); [Codex App Server docs](https://learn.chatgpt.com/docs/app-server); [Codex app-server guide (community)](https://codex.danielvaughan.com/2026/04/15/codex-app-server-complete-guide/)
- **Claude Code headless / Agent SDK:** `claude -p` with `--output-format text|json|stream-json`. `--input-format stream-json` plus `--output-format stream-json` gives a bidirectional NDJSON session (`--replay-user-messages` echoes input). Permissions come from modes/rules plus a `canUseTool` callback (SDK) or `PreToolUse` hooks; unconfigured headless runs decline risky actions. `permissionDecision: "defer"` lets a wrapper pause a tool call and resume later — [Claude Agent SDK permissions](https://code.claude.com/docs/en/agent-sdk/permissions); [headless guide (secondary)](https://ocdevel.com/podcaster/claude-code/7fdc1bc3-0a3b-42a3-8b68-c7e5f61d6b38)
- Known bug: in stream-json headless mode `PermissionRequest` hooks never fire and "ask" decisions are silently denied; use `PreToolUse` instead — [anthropics/claude-code issue #95726](https://github.com/anthropics/claude-code/issues/95726)
- Local models can back these agents: Ollama and LM Studio (and llama.cpp) serve the Anthropic Messages API, so Claude Code can be pointed at a local model through `ANTHROPIC_BASE_URL` — [Ollama Anthropic compatibility](https://docs.ollama.com/api/anthropic-compatibility); [LM Studio Anthropic compat](https://lmstudio.ai/docs/developer/anthropic-compat). Qwen3.6 explicitly supports the developer role for Codex/OpenCode — [Unsloth Qwen3.6 docs](https://unsloth.ai/docs/models/qwen3.6)

**Safe execution on Windows**
- Codex added (March 2026) native PowerShell support and a Windows-native sandbox using restricted tokens and filesystem ACLs. Two modes: *elevated* (recommended; dedicated sandbox users + firewall rules for offline mode) and *unelevated* (restricted token derived from the current user, ACL boundaries, environment-level offline controls; weaker isolation). Implementation uses a synthetic "sandbox-write" SID and write-restricted tokens — [OpenAI Codex Windows sandbox docs](https://developers.openai.com/codex/windows); [community deep-dive](https://codex.danielvaughan.com/2026/05/14/codex-cli-windows-sandbox-engineering-restricted-tokens-acls-elevated-architecture/)
- There are open bugs around mode selection (e.g. `codex exec` falling back to restricted-token despite `windows.sandbox="elevated"`) — [openai/codex issue #40158](https://github.com/openai/codex/issues/40158)
- IDE agents auto-running project-defined MCP servers without isolation is a documented 2025–2026 vulnerability class — [CSA Labs research note](https://labs.cloudsecurityalliance.org/research/csa-research-note-mcp-tool-poisoning-auto-execution-20260701/)

**Local coding model strength (vendor-reported)**
- Qwen3.6-35B-A3B: SWE-bench Verified 73.4, Terminal-Bench 2.0 51.5 — [HF card](https://huggingface.co/Qwen/Qwen3.6-35B-A3B). Qwen3.8-27B: SWE-bench Pro 61.7, Terminal-Bench 2.1 73.0 — [HF card](https://huggingface.co/Qwen/Qwen3.8-27B). Codex CLI + GPT-5.5 reported at 83.4% on Terminal-Bench 2.1 — [pinggy](https://pinggy.io/blog/best_open_source_cli_coding_agents/) (secondary)

### Inferences
- **Recommended integration order for Revia:**
  1. **ACP client in Revia.** Spawn an ACP agent via `QProcess` and speak JSON-RPC over stdio. Render its plan, diffs and permission requests in Revia's Qt UI, and route the agent's permission prompts through Revia's existing approval flow. One integration yields Claude Code, Codex, Gemini CLI and others, and each can be pointed at local llama-server through its Anthropic/OpenAI base URL.
  2. **Codex app-server** as a direct alternative if a single agent with a richer native protocol is wanted (stdio JSONL is easy with QProcess).
  3. **Claude Code headless stream-json** for one-shot tasks such as "fix this failing test" or code review, with `PreToolUse`-based policy (avoid relying on `PermissionRequest` in headless mode).
- **Build only the thin parts in-house:** keep Revia's own `GenerateCodeReview` on local Qwen with schema-constrained output. Optionally add an Aider-style tree-sitter repo map for "explain this repo" questions. Do not re-implement an edit/test agent loop; the existing agents are far ahead and free to drive.
- **Local vs cloud:** a 27B local model at ~4-bit with a limited context window on 20 GB VRAM can handle small edits and reviews. Multi-file agentic work benefits from cloud models (a large Terminal-Bench gap vs frontier agents) or from the 35B-A3B MoE with CPU expert offload. Make "coding.agent" a route whose default is local but which offers a one-click cloud escalation behind the privacy tier.
- **Execution safety:** run agents in a dedicated worktree or checkout. Prefer each agent's own sandbox (Codex elevated mode; Claude Code permission rules). Never grant blanket shell. For Revia-owned code execution, use a restricted token + job object + ACL-limited working directory, or Windows Sandbox/WSL for untrusted code. Require confirmation for network access and for writes outside the workspace.
- **LSP:** Revia could run clangd/other language servers for diagnostics as a tool (an "LSP-as-MCP" pattern). This is lower value than driving an agent that already does this; not researched.

## 5. Architecture patterns for multi-capability agents: event-driven core, actor/agent-per-capability, orchestrator + specialists, capability-based security, out-of-process plugins, config and hot-reload

### Takeaway
The systems studied converge on one shape: a long-lived core process with a message bus, and capabilities out-of-process behind a JSON-RPC boundary (MCP, ACP, Codex app-server, OVOS messagebus, HA LLM APIs). For Revia that means a Qt event-driven core owning state, persona and routing; capabilities as child processes speaking MCP/ACP over stdio or local HTTP; and permissions enforced at the core boundary. Specific pattern literature (actor frameworks, capability-security papers) was not researched, so much of this section is inference grounded in the protocol evidence above.

### Cited Findings
- Codex's architecture is one long-lived core ("app-server") with every surface (web, desktop, VS Code, CLI) as a JSON-RPC client over stdio/WebSocket, i.e. core/surface separation over a local RPC boundary — [OpenAI: Unlocking the Codex harness](https://openai.com/index/unlocking-the-codex-harness/)
- ACP runs the agent "as an independent process while Zed provides the user interface", using JSON-RPC — [Zed blog: Claude Code via ACP](https://zed.dev/blog/claude-code-via-acp)
- OVOS: components and skills interact via a messagebus; each intent is a bus event — [OVOS skill.json / technical manual](https://openvoiceos.github.io/ovos-technical-manual/411-skill_json/)
- SillyTavern server plugins run in-process in the Node server and are disabled unless `enableServerPlugins` is set, an explicit opt-in because they get full server privileges — [ST Server Plugins](https://docs.sillytavern.app/for-contributors/server-plugins/)
- MCP 2026-07-28 moved to stateless, self-describing requests with explicit server-minted handles for state, plus W3C trace context propagation in `_meta`. This favors stateless, restartable capability processes and end-to-end tracing — [MCP changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)
- MCP list results now carry `ttlMs`/`cacheScope`, and `subscriptions/listen` delivers `toolsListChanged` notifications, which provides a protocol-level basis for hot-reload of tool catalogs — [MCP changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)
- MCP Apps renders third-party UI in a sandboxed iframe with a postMessage bridge (UI isolation pattern) — [MCP blog: MCP Apps](https://blog.modelcontextprotocol.io/posts/2026-01-26-mcp-apps/)
- Process isolation matters: the CSA note documents that running tool servers with full developer privileges and no isolation led to real vulns — [CSA Labs](https://labs.cloudsecurityalliance.org/research/csa-research-note-mcp-tool-poisoning-auto-execution-20260701/). Codex's Windows sandbox shows OS-level isolation (restricted tokens, ACLs, sandbox users, firewall) is feasible on Windows — [OpenAI Codex Windows sandbox](https://developers.openai.com/codex/windows)
- The Python supply-chain compromise of LiteLLM shows the risk of pulling Python/Node plugin dependencies into a trusted process — [PyPI incident report](https://blog.pypi.org/posts/2026-04-02-incident-report-litellm-telnyx-supply-chain-attack/)

### Inferences
- **Target architecture for Revia (C++20/Qt 6):**
  - *Core (in-process, trusted):* an event bus (Qt signals/slots across `QThread` workers, or a small typed pub/sub with `std::variant` events), a conversation/state store, persona/emotion/memory, the **Router** (route → provider + privacy tier), the **Permission Broker** (evaluates each tool call against skill manifests and user policy, raises approval UI), and an audit log. Revia already has an inference scheduler, cancellation via `std::stop_token`, and an approval flow to extend.
  - *Model providers (in-process adapters):* `IChatProvider` implementations (section 1); local llama-server instances managed as child processes (existing `llamaCppServerProcess`).
  - *Capabilities (out-of-process):* MCP servers (stdio child processes or local Streamable HTTP), ACP coding agents (stdio), optional Python/Node sidecars for things with no C++ ecosystem (e.g. TTS/STT, browser automation). Each is a supervised child process with restart/backoff, a health check, and a restricted token/job object.
  - *Orchestrator + specialists:* one orchestrator loop (the companion persona) decides; specialists are routes/models (fast side model for classification/memory, coding agent, vision model) and tools. Avoid a free-form multi-agent swarm; a single orchestrator with typed sub-calls is easier to debug and secure for a solo developer.
- **Capability-based security in practice:** skills receive only the handles and scopes declared in their manifests and granted by the user (e.g. an FS-root token, a network host allow-list, an HA domain list). The core mediates all side effects. Data from tools is tagged with provenance, which Revia already tracks with `ResponseProvenance`, so untrusted content cannot silently escalate.
- **Config and hot-reload:** use declarative config (JSON/TOML) for providers, routes, skills and permissions. Watch it with `QFileSystemWatcher`, validate, and apply atomically: swap the router table, restart only the affected sidecars, and refresh tool lists via `toolsListChanged`/`ttlMs`. Keep secrets out of config (Windows Credential Manager/DPAPI).
- **IPC choice:** stdio JSON-RPC for local child processes (simplest, no ports, matches MCP/ACP/Codex); Streamable HTTP/WebSocket on `127.0.0.1` only when a sidecar must be shared or long-lived. gRPC adds build complexity under MinGW with little benefit here (inference; MinGW gRPC support not researched).

### Gaps

- Windows AppContainer/job-object APIs for sandboxing third-party sidecars were not researched directly (only via the Codex sandbox write-ups).
- No survey found of how other desktop companions (e.g. open-source VTuber/companion apps) structure plugins; that may be covered by the parallel companion-landscape research.
